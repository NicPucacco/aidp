# ADR-0019: One Database API, a backend per environment, and teams choose only the name

- **Status:** Accepted. Supersedes the t-shirt sizes in §1 of [ADR-0006](0006-database-api-and-python-compositions.md)
- **Date:** 2026-10-13
- **Phase:** infra (after ADR-0018)

## Context

Until now a `Database` was always a CloudNativePG cluster in the team's
namespace, with no backups. Teams picked a size (small, medium, large) and a
Postgres version. Production now runs on AKS (ADR-0016), and the decisions for
it were made explicitly:

| Question | Decision |
|---|---|
| Where should data live? | Both: CloudNativePG locally, Azure-managed in production |
| Recovery | No backups locally; on Azure, 3 days of backups was asked for |
| What teams control | Only the database's name |
| What happens on delete | Keep a backup |
| Cost and ownership | Team labels on the Azure database |

Two of those met Azure's limits. Flexible Server keeps built-in backups for
7 to 35 days, so 3 isn't possible; **7**, the minimum, was chosen. And when a
server is deleted, Azure keeps its backups for only 5 days, and documents
restoring them as not guaranteed. So "keep a backup" became **keep the server**.

## Decision

**1. The API is a name.** `spec.databaseName` is the only field. Size,
version, high availability and backups are the platform's decisions, made per
environment in the `environment` object (ADR-0017), not per request.

**2. The backend follows the environment.** One `database` Composition with two
template steps, each rendering only in its own environment:

| | Local (kind) | Azure (AKS) |
|---|---|---|
| Backend | CloudNativePG `Cluster`, 1 instance | Azure Database for PostgreSQL Flexible Server |
| Network | in-cluster Service | private access: a delegated subnet plus a private DNS zone, no public endpoint |
| Backups | none | 7 days, point-in-time restore |
| Version / size | platform-pinned image, 1 Gi | Postgres 17, `B_Standard_B1ms`, 32 GB, storage auto-grow |
| On delete | the cluster and its data go with it | **the server is kept** |
| Ownership | `platform.fernhill.io/owner` label | Azure tags `team`, `database`, `environment`, `managed-by` |

**3. Same contract on both.** Either backend produces a `<name>-app` Secret
with `host`, `port`, `dbname`, `user`, `password` and `uri`, so a `WebService`
binds to a database the same way everywhere. CloudNativePG writes it itself.
On Azure, the composition assembles it from the server's connection details
once they exist. The provider's own `username` is `login@server`, a Single
Server convention, so the plain login is used instead.

**4. Deletion never reaches Azure.** The `FlexibleServer` and
`FlexibleServerDatabase` are composed with management policies that exclude
`Delete`. Removing a `Database` from Git removes the Kubernetes objects, but
the server, its data and its 7 days of backups stay in Azure, tagged with the
team and database. Removing it for good is a deliberate step by a platform engineer.

**5. Secretless, again.** Crossplane's Azure provider is installed only on
AKS. It runs as a managed identity federated to its ServiceAccount, with
Contributor on a dedicated data resource group and nothing over the cluster's
own resources. The admin password is generated by the provider
(`autoGeneratePassword`); nobody sees it.

## Alternatives considered

| Option | Why not |
|---|---|
| Keep t-shirt sizes per request | Teams were choosing infrastructure they don't operate, and every size is a cost and support commitment. If a team needs more, that's a conversation, and the answer is a platform change. |
| CloudNativePG on AKS too, backups to Blob | Possible (and the API allows it later), but the platform team would then own database operations in production. Azure-managed Postgres moves patching, failover and backups to the provider. |
| Rely on Azure's 5-day dropped-server retention | Restoring is documented as not guaranteed, and 5 days is shorter than the running backups. "Keep a backup" should mean something we can count on. |
| Final `pg_dump` to Blob Storage before delete | Guarantees a portable copy and stops the cost, but needs a pre-delete job, a storage account and an identity. Keeping the server is simpler and loses nothing, at the price of cleanup. |
| Azure Service Operator instead of the Crossplane provider | Microsoft-maintained and solid. The Crossplane provider keeps one composition engine and one set of tools across the platform (ADR-0014). |
| Entra ID authentication for Postgres (no password at all) | The right end state, but every application would need workload identity and token-based connections. The password exists only in the team's Secret, generated by the provider. |

## Consequences

- **Breaking change to the API:** `size`, `version` and `engine` are gone.
  The two existing Databases (`invoice-api`, and `payment-reconciliation`
  from the agent demo), the golden paths and the MCP server are updated in
  the same PR. On a long-lived cluster, the fields would be silently dropped
  by the schema rather than rejected.
- **Agent limits now only concern WebServices.** A Database has nothing left to limit.
- **Orphaned servers cost money until removed.** They're tagged with the team
  and database, so finding them is one query. Making that a scheduled report
  is a follow-up.
- **The app's credentials are the server's admin login.** One server per
  Database keeps the blast radius to that team's data, but a per-app role
  with fewer privileges is the better end state.
- **`crossplane render` can't simulate connection details**, so the tests
  cover the Secret's shape and its "not yet" state, not the populated values.
  Only a real AKS cluster exercises those.

## What would change my mind

- Many small Databases making one server each expensive. Then one shared
  server per team, with a database per request, behind the same API.
- A team with a real need for high availability or a bigger instance. Then
  add a platform-level tier (still not a per-request knob), decided per environment.
